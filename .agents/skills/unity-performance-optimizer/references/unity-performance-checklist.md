# 性能対策を選ぶときの判断材料

症状に関係する項目だけ読む。候補をすべて適用するチェックリストではない。実行頻度と Profiler / Memory Profiler / Frame Debugger などの結果を根拠にする。

## 繰り返す検索と計算

同じ対象の GetComponent やシーン全体の検索が頻繁に走るなら、serialized reference、初期化時の取得、登録処理を検討する。キャッシュは生成・破棄・Player 切り替え時の更新も設計する。

状態が変わっていないのに再計算している処理にはイベント、dirty flag、必要な頻度のタイマーが候補。Update を別クラスへ移すだけでは計算量は減らない。空の Unity event method は、対象変更や計測に関係するときに整理する。

## GC と生成・破棄

頻繁な割り当てが確認された LINQ、文字列、コレクション、closure を対象に、再利用や単純なループを選ぶ。低頻度の初期化コードへ一律適用しない。

弾やエフェクトの生成・破棄が支配的なら pool を検討し、返却時の状態・Coroutine・イベント購読をリセットする。常駐メモリの増加も比較する。ログが原因なら頻度や対象を絞り、必要な診断情報まで削除しない。

## 描画と UI

頻繁な値の変更で Canvas rebuild が発生する場合は、更新の抑制や Canvas 分割を検討し、バッチや描画コストへの影響も比べる。操作しない Canvas の GraphicRaycaster、装飾の Raycast Target は用途を確認して外す。

Renderer の材質変更が原因なら、材質インスタンスの共有方法や MaterialPropertyBlock を候補にし、使用中の render pipeline で draw call と batching を比較する。単に API を置き換えれば高速になるとは扱わない。

画面外の処理・描画が大きい場合はカリングやチャンク単位の有効化を検討する。2D の小さなシーンに LOD や複雑な管理機構を追加しない。TMP への移行は通常の性能修正の前提ではない。

## 物理と挙動

物理更新が重いなら、まず重い Collider・接触・callback を特定する。Fixed Timestep の変更は入力感、衝突、ゲーム速度に影響するため、全体設定を変える必要があると分かった場合に挙動も検証する。

距離比較の二乗化、Animator ID のキャッシュ、CompareTag などは頻繁な呼び出しを対象にする。API の見た目だけでボトルネック扱いしない。

## アセットとロード

同期ロードや IO が停止時間を作っている場合は、既存の参照・事前ロード・非同期手段を検討する。依存関係と Unity API の実行スレッドを維持し、キャンセルと失敗経路も扱う。Addressables や新しい async ライブラリへの移行を自動で追加しない。

プラットフォーム、Unity の版、scripting backend を対象ビルドから確認する。Editor の結果だけを Standalone や WebGL の性能として報告しない。Input System の移行も、入力の性能や設計が依頼に含まれる場合に限って検討する。
